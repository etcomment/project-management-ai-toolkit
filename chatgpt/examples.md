# ChatGPT 利用例

ChatGPT で本リポジトリのコンテキストファイルを活用した利用例を示します。

すべてのサンプルは架空の情報を使用しています。実在する顧客名・案件名・個人名は含まれていません。

> [!IMPORTANT]
> AI出力は業務判断の代替ではありません。出力内容は必ず人間が確認・修正してください。
> 顧客情報・個人情報・認証情報はAIサービスに入力しないでください。

---

## 例1：プロジェクトヘルスチェック

**Use Case**
プロジェクトの現状を入力し、PM視点で危険度・課題・次アクションを整理する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/PROJECT_HEALTH_CHECK.md`

**Sanitized Input（架空データ）**

```
【案件概要】
- 種別：業務システム開発（受託）
- フェーズ：結合テスト工程
- 全体進捗：65%
- 体制：PM1名、エンジニア4名、顧客担当者2名

【状況】
- 外部連携APIの仕様が未確定のため、3機能が着手できていない
- テスト工程開始から2週間が経過しているが、バグ修正が追いつかず消化率が40%
- 顧客からの要件追加要望が2件あり、対応方針が未定
- エンジニアBが体調不良で1週間離脱予定
```

**Prompt**

```
以下のコンテキストを前提として、このプロジェクトの状況をPM視点でヘルスチェックしてください。
危険度（高・中・低）、主要な懸念点、見落とし可能性があるリスク、次アクションを整理してください。

[PM_CONTEXT.md の内容]
[PROJECT_HEALTH_CHECK.md の内容]

【現在の案件状況】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- 危険度：高
- 主要な懸念点：外部API仕様未確定によるブロッカー3件、テスト消化遅延、体制リスク
- 見落とし可能性リスク：要件追加の対応方針未定がスコープクリープに発展するリスク
- 次アクション：API仕様の確定期限を顧客と合意、要件追加の対応方針を今週中に決定、エンジニアB離脱時の体制補完計画の作成

**Human Review Points**
- 危険度の判断が実際の案件感覚と一致しているか確認する
- 「顧客と合意」などの行動提案が自社・顧客の関係性に適しているか確認する
- 次アクションの優先順位が現場状況に合っているか調整する

## 例2：進捗報告の作成

**Use Case**
今週の作業状況を入力し、社内向け・顧客向けの進捗報告文を整理する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/STATUS_REPORT_CONTEXT.md`
- `prompts/status-report.md`

**Sanitized Input（架空データ）**

```
【今週の状況】
- 完了：ユーザー管理機能の単体テスト完了、帳票出力機能の実装完了
- 進行中：受注管理機能のテスト（進捗60%）
- 遅延：在庫連携機能が外部API仕様待ちで着手不可（1週間遅延見込み）
- 来週予定：受注管理機能テスト完了、在庫連携機能の仕様確認（顧客と打ち合わせ予定）
- 課題：外部APIの仕様確定が遅れており、スケジュールへの影響を精査中
```

**Prompt**

```
以下のコンテキストと今週の状況をもとに、進捗報告を整理してください。
社内向けサマリーと、顧客向け報告のたたき台を作成してください。

[PM_CONTEXT.md の内容]
[STATUS_REPORT_CONTEXT.md の内容]

【今週の状況（機密情報はマスキング済み）】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- 社内向けサマリー：今週完了事項・進行中・遅延事項・リスクを箇条書きで整理
- 顧客向け報告たたき台：「今週の進捗」「遅延事項と理由」「来週の予定」を丁寧な文体で整理

**Human Review Points**
- 顧客向け文面のトーンが実際の顧客との関係性に合っているか確認する
- 遅延の説明が事実と一致しているか確認する
- 顧客提出前に上長・担当者のレビューを受ける

## 例3：課題・リスクレビュー

**Use Case**
課題一覧を入力し、抜け漏れ・優先度・エスカレーション候補を整理する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/ISSUE_RISK_CONTEXT.md`
- `prompts/issue-risk-review.md`

**Sanitized Input（架空データ）**

```
【課題一覧】
No. | 課題内容 | 担当 | 期限 | 影響
1 | 外部APIの仕様が未確定 | 顧客A担当者 | 未定 | 3機能が着手不可
2 | 帳票レイアウトの承認が得られていない | PM | 来週金曜 | 印刷機能テスト開始不可
3 | 旧システムからのデータ移行仕様が曖昧 | エンジニアB | 未定 | 移行工程全体に影響
4 | 本番環境の構築手順が未定 | インフラ担当 | 未定 | リリース直前に発覚するリスク
```

**Prompt**

```
以下のコンテキストと課題一覧をもとに、課題のレビューをしてください。
優先度の見直し、担当者・期限が不明な課題の指摘、エスカレーション候補の提示をお願いします。

[PM_CONTEXT.md の内容]
[ISSUE_RISK_CONTEXT.md の内容]

【課題一覧（機密情報はマスキング済み）】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- 優先度整理：課題1・3・4を高優先度として分類
- 担当・期限不明の指摘：課題1・3・4は期限未定のためリスクが高い
- エスカレーション候補：課題1（外部APIの仕様未確定）は顧客側の意思決定が必要なため上長エスカレーションを検討

**Human Review Points**
- 優先度の判断が実際の案件判断と合っているか確認する
- エスカレーション提案が組織の関係性・状況に適しているか確認する
- 最終的なエスカレーションの判断はPMと上長が行う

## 例4：顧客向け説明文のたたき台

**Use Case**
遅延発生時に、顧客への説明文のたたき台を作成する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/CLIENT_COMMUNICATION_CONTEXT.md`
- `prompts/client-communication.md`

**Sanitized Input（架空データ）**

```
【状況】
- 在庫連携機能が、外部API仕様の確定遅れにより1週間遅延する見込み
- 遅延の原因：顧客提供の外部APIの仕様書の改訂版が届いていないため
- 影響：在庫連携機能のリリースが当初予定より1週間後ろ倒しになる
- 提案：在庫連携機能を除いた形で当初リリース日に第1フェーズリリースを実施し、
         在庫連携機能は1週間後に追加リリースする
- 顧客への依頼：API仕様書の改訂版を今週木曜日までに提供いただきたい
```

**Prompt**

```
以下の状況をもとに、顧客向けの状況説明・提案メールのたたき台を作成してください。
事実の説明、影響範囲、対応案、顧客への依頼事項を含めてください。

[PM_CONTEXT.md の内容]
[CLIENT_COMMUNICATION_CONTEXT.md の内容]

【状況（機密情報はマスキング済み）】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- 件名：「〇〇機能の対応状況について」
- 本文：遅延事実の説明、原因の説明、提案内容（段階リリース案）、顧客への依頼事項を含む丁寧な文体のたたき台

**Human Review Points**
- 顧客との関係性・過去のやりとりを踏まえてトーンを調整する
- 事実と異なる表現がないか確認する
- 送信前に上長・担当者のレビューを受ける
- AI生成のたたき台をそのまま送信しない

## 例5：炎上初動72時間の整理

**Use Case**
トラブル発生直後に、事実・影響・初動対応・未確認事項を整理する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/FIRE_RESPONSE_FIRST_72H.md`
- `prompts/fire-response.md`

**Sanitized Input（架空データ）**

```
【発生事象】
- 本番リリース後、受注データが一部欠損していることが顧客から報告された
- 発覚時刻：リリース翌日の午前10時
- 影響範囲：昨日リリース後から当日朝9時までの受注データ（件数は調査中）
- 暫定原因：移行バッチの処理順序に不備がある可能性（調査中）
- 現在の対応：本番環境を旧システムに切り戻し中

【未確認事項】
- 欠損データの件数・内容
- 顧客業務への実際の影響（受注漏れが発生しているか）
- 根本原因の特定（調査中）
- データ復旧の可否と方法
```

**Prompt**

```
以下のトラブル状況をもとに、炎上初動の対応を整理してください。
事実と推測の切り分け、影響範囲、今日中に確認すべきこと、
顧客に伝えるべきこと、社内で決めるべきこと、72時間以内の対応計画を整理してください。

[PM_CONTEXT.md の内容]
[FIRE_RESPONSE_FIRST_72H.md の内容]

【現在の状況（機密情報はマスキング済み）】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- 事実と推測の切り分け：確定事実（データ欠損の発生、切り戻し対応中）と調査中事項（件数・原因）を分けて整理
- 影響範囲：リリース後から切り戻しまでの受注データ、業務影響は確認中
- 今日中に確認すべきこと：欠損データの件数・内容、業務影響の有無、根本原因の仮説
- 顧客に伝えるべきこと：発生事実・切り戻し対応中・調査中である旨・次回連絡予定時刻
- 社内で決めるべきこと：エスカレーション先・顧客対応窓口・対外コミュニケーションの責任者
- 72時間対応計画：今日中に原因特定、明日中にデータ復旧方針決定、72時間以内に顧客へ詳細報告

**Human Review Points**
- 事実と推測の切り分けが正確かどうかを現場情報と照合する
- 顧客への連絡タイミング・内容は上長と合意してから実施する
- 対外コミュニケーションはAI出力をたたき台として、必ず人間が判断・承認する
- 法的・契約的な影響が生じる場合は法務・上長に確認する
