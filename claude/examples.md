# Claude Examples / Claudeでの利用例

---

## このファイルの目的

Claudeで `contexts/` を使う際の具体的な入力例・プロンプト例・期待する出力例を示します。

> [!IMPORTANT]
> すべてのサンプルは架空データです。実在する顧客情報・案件情報・個人情報は含みません。
> AI出力は業務判断の代替ではありません。出力内容は必ず人間が確認してください。

---

## Example 1: プロジェクトヘルスチェック

### Use Case

開発中盤のプロジェクトについて、PM視点でヘルスチェックを行う。

### 使用するファイル

- `contexts/PM_CONTEXT.md`
- `contexts/PROJECT_HEALTH_CHECK.md`

### Sanitized Input

```text
案件：サンプル案件（架空）
フェーズ：開発中盤
進捗：全体60%
遅れている作業：外部連携機能、テスト設計
未解決課題：顧客確認待ち2件、仕様未確定1件
体制上の懸念：レビュー担当者が不足
```

### Prompt

```text
以下のコンテキストを前提として、プロジェクト状況をPM視点でヘルスチェックしてください。

【PM_CONTEXT.md の内容】
（ここにcontexts/PM_CONTEXT.mdを貼り付ける）

【PROJECT_HEALTH_CHECK.md の内容】
（ここにcontexts/PROJECT_HEALTH_CHECK.mdを貼り付ける）

【案件状況（架空）】
案件：サンプル案件
フェーズ：開発中盤
進捗：全体60%
遅れている作業：外部連携機能、テスト設計
未解決課題：顧客確認待ち2件、仕様未確定1件
体制上の懸念：レビュー担当者が不足
```

### Expected Output

- 状況要約
- 危険度（高・中・低）
- 主要な懸念点
- 顧客に確認すべきこと
- 次アクション

### Human Review Points

- 危険度の判断は案件の実態と合っているか
- 懸念点に見落としはないか
- 顧客への確認事項の表現は適切か
- 出力をそのまま顧客提出・社内報告に使わない

## Example 2: 進捗報告の整理

### Use Case

週次の作業状況をもとに、社内向け・顧客向け・上長向けの進捗報告をまとめる。

### 使用するファイル

- `contexts/PM_CONTEXT.md`
- `contexts/STATUS_REPORT_CONTEXT.md`

### Sanitized Input

```text
今週完了した作業：
- 基本設計レビュー（完了）
- テスト環境構築（完了）

未完了の作業：
- 詳細設計書 作成中（進捗70%）

遅延している作業：
- 外部API連携設計（2日遅延）

課題：
- 外部システムの仕様確認が未完了

顧客確認待ち：
- 画面遷移仕様の確認（依頼済み、回答待ち）

来週の予定：
- 詳細設計書 完成
- 外部連携設計の再調整
```

### Prompt

```text
以下のコンテキストを前提として、今週の進捗報告を整理してください。

【PM_CONTEXT.md の内容】
（ここにcontexts/PM_CONTEXT.mdを貼り付ける）

【STATUS_REPORT_CONTEXT.md の内容】
（ここにcontexts/STATUS_REPORT_CONTEXT.mdを貼り付ける）

【今週の状況（架空）】
（Sanitized Inputの内容を貼り付ける）

以下の3種類で整理してください：
1. 社内向け進捗報告
2. 顧客向け進捗報告
3. 上長向けサマリー
```

### Expected Output

- 社内向け進捗報告
- 顧客向け進捗報告
- 上長向けサマリー
- 次アクション一覧

### Human Review Points

- 事実と一致しているか
- 顧客向けの表現トーンは適切か
- 遅延の説明が過度に楽観的または悲観的になっていないか
- 契約・費用・納期に関する記述は人間が確認する

## Example 3: 炎上初動72時間の整理

### Use Case

本番環境で障害が発生した直後に、事実・影響・初動対応を整理する。

### 使用するファイル

- `contexts/PM_CONTEXT.md`
- `contexts/FIRE_RESPONSE_FIRST_72H.md`

### Sanitized Input

```text
何が起きたか：
- 本番環境の特定機能で処理エラーが発生

いつ発生したか：
- 平日 午前10時頃に顧客から連絡

顧客影響：
- 当該機能が利用不可
- 影響ユーザー数：確認中

社内影響：
- 開発チームが調査対応中

現在分かっている事実：
- エラーログにDB接続タイムアウトが記録されている

まだ分かっていないこと：
- 原因の特定
- 影響範囲の全容

すでに実施した対応：
- 顧客へ第一報（電話）
- 開発チームに調査依頼
```

### Prompt

```text
以下のコンテキストを前提として、炎上初動の状況を整理してください。

【PM_CONTEXT.md の内容】
（ここにcontexts/PM_CONTEXT.mdを貼り付ける）

【FIRE_RESPONSE_FIRST_72H.md の内容】
（ここにcontexts/FIRE_RESPONSE_FIRST_72H.mdを貼り付ける）

【現在の状況（架空）】
（Sanitized Inputの内容を貼り付ける）
```

### Expected Output

- 事実と推測の切り分け
- 影響範囲の現時点での整理
- 今日中に確認すべきこと
- 顧客に伝えるべきこと（たたき台）
- 72時間以内の対応計画

### Human Review Points

- 事実と推測が混在していないか
- 顧客への説明文はトーンが適切か
- 契約・保証・費用負担に関する表現は法務・上長に確認する
- 対応計画の実現可能性は人間が判断する

## Example 4: スコープ変更の整理

### Use Case

顧客から仕様変更の要望が来た際に、影響範囲・工数・納期への影響を整理する。

### 使用するファイル

- `contexts/PM_CONTEXT.md`
- `contexts/SCOPE_CHANGE_CONTEXT.md`

### Sanitized Input

```text
変更要望：
- ダッシュボード画面に月次集計グラフを追加してほしい

変更が出た背景：
- 運用開始後に現場から要望が上がった

当初スコープ：
- ダッシュボードは一覧表示のみ

追加になりそうな作業：
- グラフ表示コンポーネント開発
- 月次集計ロジックの追加
- テスト追加

影響しそうな機能：
- レポート出力機能（データ参照箇所が重複する可能性あり）

納期制約：
- 2週間後のリリース予定が固定

顧客に確認したいこと：
- 優先度（必須か要望か）
- 承認フロー
```

### Prompt

```text
以下のコンテキストを前提として、スコープ変更の影響を整理してください。

【PM_CONTEXT.md の内容】
（ここにcontexts/PM_CONTEXT.mdを貼り付ける）

【SCOPE_CHANGE_CONTEXT.md の内容】
（ここにcontexts/SCOPE_CHANGE_CONTEXT.mdを貼り付ける）

【変更要望の状況（架空）】
（Sanitized Inputの内容を貼り付ける）
```

### Expected Output

- 変更内容の整理
- 当初スコープとの差分
- 影響範囲
- 工数影響（概算）
- 納期影響
- 顧客確認事項
- エスカレーション要否

### Human Review Points

- 工数・納期の見通しは人間が判断する
- 費用・契約変更に関する表現は法務・上長に確認する
- 顧客への回答文はそのまま送付しない
- エスカレーション要否は組織の判断を優先する

---

## 安全上の注意

> [!CAUTION]
> - すべての例は架空データです
> - 実案件情報をそのまま入力しないでください
> - 顧客名・個人名・会社名・契約情報・認証情報は必ずマスキングしてください
> - AI出力は業務判断の代替ではありません
> - 顧客提出・社内報告・契約判断・納期回答には必ず人間が確認してください
