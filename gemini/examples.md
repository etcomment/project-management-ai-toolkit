# Gemini 利用例

Gemini で本リポジトリのコンテキストファイルを活用した利用例を示します。

すべてのサンプルは架空の情報を使用しています。実在する顧客名・案件名・個人名は含まれていません。

> [!IMPORTANT]
> AI出力は業務判断の代替ではありません。出力内容は必ず人間が確認・修正してください。
> 顧客情報・個人情報・認証情報はAIサービスに入力しないでください。

---

## 例1：プロジェクトヘルスチェック

**Use Case**
プロジェクトの現状を入力し、PM視点で危険度・課題・次アクションを整理する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/PROJECT_HEALTH_CHECK.md`

**Sanitized Input（架空データ）**

```
【案件概要】
- 種別：Webアプリ開発（受託）
- フェーズ：設計・開発並行フェーズ
- 全体進捗：45%
- 体制：PM1名、エンジニア3名、顧客担当者1名

【状況】
- 画面設計の承認が顧客側の都合で2週間遅延している
- 未承認の画面設計のまま開発を進めているため、手戻りリスクがある
- テスト担当が未アサインで、テスト計画が未作成
- 顧客から機能追加の要望が3件あり、見積・調整が未実施
```

**Prompt**

```
以下のコンテキストを前提として振る舞ってください。
プロジェクト状況をPM視点でヘルスチェックし、
危険度（高・中・低）、主要な懸念点、見落とし可能性があるリスク、次アクションを整理してください。

[PM_CONTEXT.md の内容]
[PROJECT_HEALTH_CHECK.md の内容]

【現在の案件状況（機密情報はマスキング済み）】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- 危険度：中〜高
- 主要な懸念点：画面設計未承認のまま開発継続、テスト担当未アサイン、機能追加要望の未処理
- 見落とし可能性リスク：未承認設計による手戻りがスケジュールに与える影響が未試算
- 次アクション：画面設計承認の期限を顧客と合意、テスト担当のアサイン計画を今週中に作成、追加要望の対応方針決定

**Human Review Points**
- 危険度の判断が実際の案件感覚と一致しているか確認する
- 次アクションの優先順位が現場状況に合っているか調整する
- 「顧客と合意」などの行動提案が自社・顧客の関係性に適しているか確認する

## 例2：進捗報告の作成

**Use Case**
今週の作業状況を入力し、社内向け・顧客向けの進捗報告文を整理する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/STATUS_REPORT_CONTEXT.md`
- `prompts/status-report.md`

**Sanitized Input（架空データ）**

```
【今週の状況】
- 完了：検索機能の単体テスト完了、ログイン機能の設計書レビュー完了
- 進行中：ユーザー管理機能の開発（進捗70%）
- 遅延：通知機能が要件未確定のため着手不可（2週間遅延見込み）
- 来週予定：ユーザー管理機能の完成・結合テスト開始、通知機能の要件確認（顧客と打ち合わせ予定）
- 課題：通知機能の要件が顧客の社内調整待ちで確定していない
```

**Prompt**

```
以下のコンテキストと今週の状況をもとに、進捗報告を整理してください。
社内向けサマリーと顧客向け報告のたたき台を作成してください。

[PM_CONTEXT.md の内容]
[STATUS_REPORT_CONTEXT.md の内容]

【今週の状況（機密情報はマスキング済み）】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- 社内向けサマリー：今週完了事項・進行中・遅延事項・リスクを箇条書きで整理
- 顧客向け報告たたき台：「今週の進捗」「遅延事項と理由」「来週の予定」を丁寧な文体で整理

**Human Review Points**
- 顧客向け文面のトーンが実際の顧客との関係性に合っているか確認する
- 遅延の説明が事実と一致しているか確認する
- 顧客提出前に上長・担当者のレビューを受ける

## 例3：課題・リスクレビュー

**Use Case**
課題一覧を入力し、抜け漏れ・優先度・エスカレーション候補を整理する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/ISSUE_RISK_CONTEXT.md`
- `prompts/issue-risk-review.md`

**Sanitized Input（架空データ）**

```
【課題一覧】
No. | 課題内容 | 担当 | 期限 | 影響
1 | 通知機能の要件が未確定 | 顧客B担当者 | 未定 | 2機能が着手不可
2 | テスト環境のサーバー設定が未完了 | インフラ担当 | 来週月曜 | テスト工程全体に影響
3 | 旧システムデータの形式変換仕様が曖昧 | エンジニアA | 未定 | 移行テストが開始できない
4 | レスポンス速度の要件が未定義 | PM | 未定 | 性能テストの基準が設定できない
```

**Prompt**

```
以下のコンテキストと課題一覧をもとに、課題のレビューをしてください。
優先度の整理、担当者・期限が不明な課題の指摘、エスカレーション候補の提示をお願いします。

[PM_CONTEXT.md の内容]
[ISSUE_RISK_CONTEXT.md の内容]

【課題一覧（機密情報はマスキング済み）】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- 優先度整理：課題2（テスト環境）を最高優先度、課題1・3・4を高優先度として分類
- 担当・期限不明の指摘：課題1・3・4は期限未定のためリスクが高い
- エスカレーション候補：課題1（要件未確定）は顧客側の意思決定が必要なため上長エスカレーションを検討

**Human Review Points**
- 優先度の判断が実際の案件判断と合っているか確認する
- エスカレーション提案が組織の関係性・状況に適しているか確認する
- 最終的なエスカレーションの判断はPMと上長が行う

## 例4：週次定例アジェンダ作成

**Use Case**
今週の状況を入力し、週次定例のアジェンダと事前共有資料の構成案を作成する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/WEEKLY_MEETING_CONTEXT.md`
- `prompts/weekly-meeting.md`

**Sanitized Input（架空データ）**

```
【今週の定例に向けた状況】
- 参加者：PM、エンジニアリーダー、顧客担当者
- 今週完了：ユーザー管理機能の開発完了
- 懸案事項：通知機能の要件が未確定（顧客側確認中）
- 来週の重要イベント：結合テスト開始予定
- 顧客に確認したいこと：通知機能の要件確定時期、追加要望3件の優先度
- 共有したいリスク：テスト工程のリソースが不足している可能性
```

**Prompt**

```
以下の状況をもとに、週次定例のアジェンダ案と進行メモを作成してください。
各議題に想定所要時間と目的（報告・確認・決定）を付けてください。

[PM_CONTEXT.md の内容]
[WEEKLY_MEETING_CONTEXT.md の内容]

【今週の定例に向けた状況（機密情報はマスキング済み）】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- アジェンダ案：前回議事録確認（5分）、今週の進捗報告（10分）、懸案事項の確認・決定（15分）、来週の予定確認（5分）、その他（5分）
- 各議題の目的明記（報告/確認/決定）
- 顧客への確認事項リスト

**Human Review Points**
- アジェンダの構成が実際の定例の慣習・時間配分に合っているか調整する
- 顧客への確認事項の表現が関係性に合ったトーンか確認する

## 例5：スコープ変更の整理

**Use Case**
顧客から追加要望があった際に、スコープ変更の影響と対応方針のたたき台を整理する

**使用するファイル**
- `contexts/PM_CONTEXT.md`
- `contexts/SCOPE_CHANGE_CONTEXT.md`
- `prompts/scope-change.md`

**Sanitized Input（架空データ）**

```
【追加要望の概要】
- 要望内容：CSVエクスポート機能の追加（当初仕様に含まれていなかった）
- 要望元：顧客担当者より口頭で依頼
- 要望の背景：既存業務ツールとのデータ連携に必要とのこと
- 現状：要件定義フェーズ完了後、開発フェーズ進行中
- 影響範囲：バックエンド開発2日、フロントエンド開発1日、テスト1日の追加見込み
- 契約：変更管理手続きが契約に含まれている
```

**Prompt**

```
以下のスコープ変更要望を整理してください。
変更の影響範囲、リスク、対応方針の選択肢、顧客への確認事項を整理してください。

[PM_CONTEXT.md の内容]
[SCOPE_CHANGE_CONTEXT.md の内容]

【追加要望の概要（機密情報はマスキング済み）】
（上記Sanitized Inputを貼り付ける）
```

**Expected Output（例）**

- 変更影響範囲：工数約4日増加、スケジュール影響は並行対応可否による
- リスク：口頭での要望のため、要件の詳細・優先度が未確定
- 対応方針の選択肢：①変更管理手続きを経て追加対応する、②今回スコープ外として次フェーズに先送りする
- 顧客への確認事項：要件の詳細・優先度の確認、変更管理手続きの開始確認

**Human Review Points**
- 工数見積もりが実際のエンジニアの見立てと一致しているか確認する
- 契約・変更管理手続きの内容は実際の契約書・担当者に確認する
- 顧客への対応方針提示は法務・上長と相談してから実施する
